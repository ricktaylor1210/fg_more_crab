# 更多螃蟹项目开发进度评估

## 1. 结论概览

基于当前 spec 文档与 `fg_more_crab.zip` 中的实际工程内容，这个项目目前处于：

- **策划设计已经比较完整**：生态、系统、Boss、世界生成、版本路线都定义清楚。
- **实现层仍在 V1.0 早期阶段**：真正落地到行为包的内容，主要还是**基础螃蟹实体雏形**。
- **资源制作明显领先于玩法实现**：模型、贴图、动画已经预铺了大量 Boss / 海盗蟹 / 装备内容，但多数还没有接入行为、生成、掉落、交互与玩法闭环。

如果按“**玩家可实际游玩到的功能**”来评估，而不是按“资源资产是否存在”来评估：

- **V1.0 完成度：约 25% ~ 35%**
- **V1.1 完成度：约 5% ~ 10%**
- **V1.2 完成度：约 0% ~ 5%**
- **整个路线图总体完成度：约 20% 左右**

> 这个估算是按当前压缩包可见实现做的“可玩性口径”判断，不按贴图/模型数量计数。

## 2. 当前已经完成了什么

### 2.1 已经落地的核心内容

#### A. 基础螃蟹实体已经有第一版实现

当前行为包已经存在 3 个实体：

- `fg:fg_crab`
- `fg:fg_crab_help`
- `fg:fg_crab_aggressive`

并且已经具备：

- 基础生命、移动、碰撞、受击与掉落配置
- 出生规则（海滩 / 海洋 / 沙地 / 砾石地表）
- 基础随机游走、看向玩家、随机观察
- 受击后的愤怒逻辑
- 攻击模式切换（左钳 / 右钳 / 双钳）
- 配套动画控制器与资源包实体定义

这说明你已经把“**基础螃蟹作为一个能正常生成、能动、能攻击、能掉落的实体**”这件事跑通了。

#### B. 基础掉落与基础材料原型已接通

当前可见已注册的物品行为包括：

- `fg:crab_claws`（实际文案是生蟹肉）
- `fg:crab_shell_powder`（蟹壳碎片）

这意味着最基础的“**打螃蟹 → 掉材料**”链路已经有雏形。

#### C. 普通生态生成已经接通

目前已有基础螃蟹生成规则：

- 生成地形：沙子 / 红沙 / 砾石
- 生成环境：海滩 / 海洋
- 亮度与高度有约束
- 有群体规模与密度控制

这部分已经具备“生态化存在”的最小可玩基础，不是单纯 summon 测试实体。

## 4. 当前项目最关键的问题

### 4.1 资源制作和玩法实现严重不同步

你现在不是“内容太少”，而是“**玩法骨架太薄，资源资产过多**”。

换句话说：

- 美术/模型/动画准备得比行为开发快很多；
- 但行为包、生成规则、交互系统、掉落与配方闭环没有同步跟上；
- 这会导致后面维护成本上升，因为很多资源虽然存在，但并没有真正进入可测试、可平衡、可迭代状态。

### 4.2 命名和设计抽象还没有完全收口

spec 中定义的是：

- `crab_normal`
- `crab_mineral`
- `crab_pirate`
- `crab_boss_xxx`

但当前实现层是：

- `fg_crab`
- `fg_crab_help`
- `fg_crab_aggressive`

这不一定是错误，但说明：

- 当前工程还带有较强“试验性”；
- 还没有完全收束到 spec 的正式实体模型；
- 如果现在继续大量加内容，不先收口实体体系，后面会反复重命名、改引用、改掉落、改资源映射。

### 4.3 V1.0 还没有形成真正的可玩闭环

从 spec 看，V1.0 的核心不是“多几个螃蟹贴图”，而是形成这条闭环：

1. 海边遇到螃蟹
2. 击杀/捕获获得材料
3. 做食物 / 基础装备 / 驯服道具
4. 驯服螃蟹
5. 给螃蟹装背包
6. 用捕蟹笼扩张资源获取

而当前项目只完成了这条链路中的前半段入口，后半段系统价值还没有落地。

## 5. 下一步最应该做什么

## 5.1 战略判断

**下一步不应该继续铺 Boss、装备、终局资源。**

最合理的方向是：

> **先把 V1.0 做成一个完整可玩的垂直切片（vertical slice）。**

也就是先确保玩家能完整体验：

- 遇到螃蟹
- 打 / 捕
- 掉材料
- 做基础物品
- 触发一个核心系统

只有 V1.0 闭环成立，后面的 Boss 与套装才有稳定基座。

---

## 5.2 战术上，建议你下一项直接开发的内容

### 第一优先级：先收口“基础螃蟹实体架构”

建议你先做一次小型重构，而不是马上上 Boss：

#### 目标

把当前的 `fg_crab / fg_crab_help / fg_crab_aggressive` 整理成一个清晰、可扩展的基础生态体系。

#### 建议动作

1. 统一命名策略，决定：
   - 是保留 3 个独立实体；
   - 还是改成 1 个基础实体 + 性格/状态属性切换。
2. 对齐 spec 中的正式命名规范。
3. 固化“新增一个螃蟹实体必须具备哪些文件”：
   - behavior entity
   - spawn rule
   - loot table
   - resource entity
   - lang
   - item/icon（如需要）
4. 把普通螃蟹的行为和 spec 对齐到位。

#### 为什么这一步最重要

因为你后面的矿物螃蟹、海盗螃蟹、Boss，全都要复用这个基础骨架。

如果基础骨架现在不收口，后面越做越乱。

---

### 第二优先级：直接实现 TASK-02 矿物螃蟹

这是我认为**最适合作为下一个正式开发任务**的内容。

#### 原因

- 它和你现有基础螃蟹复用度最高；
- 当前资源包里已经有矿物螃蟹贴图，资产不是瓶颈；
- 相比驯服背包、捕蟹笼、海盗偷包，它的逻辑复杂度更可控；
- 它能验证“**同一骨架扩出多个玩法实体**”这件事是否成立。

#### 建议最小实现范围（MVP）

1. 新建矿物螃蟹行为实体
2. 增加 `ore_type` 属性
3. 洞穴 / 矿洞生成规则
4. 靠近矿石时触发“吃矿”事件
5. 吃矿后获得短时抗性 / 护甲 Buff
6. 根据 `ore_type` 切换掉落表

#### 这一项做完后，你会得到什么

- 你会验证实体复用框架是否合理；
- 你会把 V1.0 的“生态丰富度”明显拉起来；
- 你会得到第一个真正意义上的“差异化螃蟹玩法”。

---

### 第三优先级：补一个最小可用经济闭环

在矿物螃蟹之后，不建议立刻上 Boss，而建议二选一：

- **方案 A：捕蟹笼 MVP**
- **方案 B：基础料理 + 基础配方 MVP**

我更偏向：

> **先做基础料理 + 配方 MVP，再做捕蟹笼。**

因为这样可以先让“材料有去处”，避免掉落只是仓库垃圾。

---

## 6. 我建议的近期开发顺序

### 方案：1 个小重构 + 3 个功能里程碑

#### 里程碑 0：架构收口

- 统一实体命名
- 统一基础螃蟹骨架
- 清理试验性分叉

#### 里程碑 1：矿物螃蟹 MVP

- 完成实体 / 生成 / 吃矿 / 掉落

#### 里程碑 2：基础料理与配方 MVP

- 至少让生蟹肉、蟹壳碎片有明确用途
- 做出 2~3 个可合成可使用的基础物品

#### 里程碑 3：捕蟹笼 MVP 或驯服 MVP

二选一：

- 如果你想优先做“资源循环”，先做捕蟹笼；
- 如果你想优先做“模组辨识度”，先做驯服系统。

---

## 7. 不建议你现在做的事

当前阶段，不建议你优先投入这些方向：

- 继续新增 Boss 美术资源
- 继续新增终局装备模型
- 先做循声蟹守卫
- 先做深渊神庙
- 先做四大 Boss 场景生成

原因很简单：

> 当前项目最缺的不是“终局内容”，而是“前中期可持续游玩的基本闭环”。

---

## 8. 最终判断

这个项目的设计面已经足够大，**现在真正需要的是“收口”和“打通”**。

一句话概括当前状态：

> **你已经完成了“螃蟹模组的美术与概念搭架子”，但还没有完成“V1.0 可玩产品”的闭环。**

一句话概括下一步：

> **先统一基础螃蟹架构，然后优先做 TASK-02 矿物螃蟹，把 V1.0 从“资源堆积”推进到“玩法成型”。**
