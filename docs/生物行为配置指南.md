# 生物行为配置指南

## 1. 文档定位
这份文档不是通用的 Bedrock 生物教程，而是基于当前仓库已经落地的螃蟹实体配置做的整理。

本文主体仍以最早接线的 3 个原型螃蟹为行为状态机样本，因为它们最适合解释 `properties`、`component_groups`、`events` 和行为动画控制器之间的关系。

当前项目实际范围已经扩展到：

- 7 个正式普通生态螃蟹实体
- 9 个独立矿物螃蟹实体
- 3 个海盗螃蟹职业实体
- 5 个捕蟹笼品质实体
- 服务端脚本驱动的矿物蟹吃矿、海盗蟹偷窃和捕蟹笼捕获逻辑

原型样本涉及的行为包文件有：

- `fg_more_crabBehaviorPack/entities/fg_crab.json`
- `fg_more_crabBehaviorPack/entities/fg_crab_help.json`
- `fg_more_crabBehaviorPack/entities/fg_crab_aggressive.json`
- `fg_more_crabBehaviorPack/spawn_rules/fg_crab.json`
- `fg_more_crabBehaviorPack/spawn_rules/fg_crab_help.json`
- `fg_more_crabBehaviorPack/spawn_rules/fg_crab_aggressive.json`
- `fg_more_crabBehaviorPack/loot_tables/entities/fg_crab.json`
- `fg_more_crabBehaviorPack/loot_tables/entities/fg_crab_help.json`
- `fg_more_crabBehaviorPack/loot_tables/entities/fg_crab_aggressive.json`
- `fg_more_crabBehaviorPack/animations/fg_crab.animation.json`
- `fg_more_crabBehaviorPack/animation_controllers/fg_crab.ac.json`

这份指南的目标有两个：

1. 说明当前项目里一只生物在行为包里到底是怎么跑起来的。
2. 说明为什么当前配置要拆成这些文件、这些字段、这些事件，而不是全部堆在一个 JSON 里。

## 2. 当前项目里的行为配置总览
按当前仓库的实现，一只实体真正跑起来，至少会经过下面这条链路：

```text
entities/*.json
  -> 定义实体基础属性、AI、事件、组件组、可同步属性
  -> spawn_rules/*.json
  -> 决定自然生成条件
  -> loot_tables/entities/*.json
  -> 决定死亡掉落
  -> animations/*.json（行为包）
  -> 提供“事件时间轴”
  -> animation_controllers/*.json（行为包）
  -> 根据 query / property 驱动事件切换
```

为什么要这样拆：

- `entities/*.json` 负责“它是什么、能做什么”。
- `spawn_rules/*.json` 负责“它在哪里出现”，这样同一个实体可以换多套生成方案，不必污染实体本体。
- `loot_tables/*.json` 负责“它死后掉什么”，这样掉落可以单独平衡，不必改 AI 文件。
- 行为包里的 `animations` 和 `animation_controllers` 不是做模型动作的，它们更像服务端逻辑定时器和状态机，用于在某个时机触发事件、切换组件组、重置属性。

这也是当前项目最重要的设计思路：

> 实体本体负责声明状态，组件组负责承载可切换能力，事件负责切换，行为动画控制器负责判断什么时候切换。

## 3. 原型三只螃蟹的行为差异

| 实体 | identifier | 核心定位 | 生命值 | 移速 | 默认攻击人格 | 受伤群体响应 |
|---|---|---|---:|---:|---|---|
| 普通螃蟹 | `fg:crab` | 受伤后自己应战，附近同类逃跑 | 10 | 0.15 | `calm` | 通过受伤事件触发附近普通螃蟹避让 |
| 护群螃蟹 | `fg:crab_help` | 受伤时同类型会联动进入愤怒 | 10 | 0.15 | `calm` | 出生即带 `minecraft:angry` 组件组 |
| 暴躁螃蟹 | `fg:crab_aggressive` | 更高数值，更强攻击循环，更稀有 | 12 | 0.17 | `aggressive` | 出生即带 `minecraft:angry` 组件组 |

为什么先看差异：

- 文档后面会反复提到“共用骨架”和“变体参数”。
- 当前项目不是三套完全不同的 AI，而是一套共用结构加少量参数差异和少量额外逻辑。
- 如果不先把这一点看清，后续新增实体时很容易复制粘贴出三套越来越分叉的 JSON，最后很难维护。

## 4. `entities/*.json` 是行为配置核心

原型三个实体文件都使用同一个总结构：

```json
{
  "format_version": "1.21.50",
  "minecraft:entity": {
    "description": {},
    "component_groups": {},
    "components": {},
    "events": {}
  }
}
```

为什么 `entities` 文件一定要分成这 4 块：

- `description` 是静态声明，定义标识、属性、脚本入口。
- `component_groups` 是可开关的行为模块，适合承载“状态”。
- `components` 是默认常驻能力。
- `events` 是运行时切换入口。

如果把所有行为都直接写死在 `components`：

- 你没法优雅地做“左攻击 / 右攻击 / 双击攻击”的切换。
- 你没法临时进入“避让状态”再退出。
- 你会被迫用多个重复实体去表示多个状态，扩展成本极高。

### 4.1 `description`

当前最关键的是下面几类字段。

#### 4.1.1 `identifier`

示例：

```json
"identifier": "fg:crab"
```

作用：

- 这是行为包里的实体主键。
- `spawn_rules`、资源包 `client_entity`、语言文件、召唤命令都要依赖它。

为什么必须稳定：

- 这是跨文件关联的锚点。
- 一旦这里变了，行为包能过语法，不代表资源包还能渲染，也不代表生成规则还能生效。

#### 4.1.2 `spawn_category`

当前都写成：

```json
"spawn_category": "creature"
```

为什么这么做：

- 当前螃蟹的世界定位更接近环境生物，而不是怪物。
- 即使它们具备攻击能力，也仍然被归入自然生态型生物池，这样更符合海滩生态的预期。

#### 4.1.3 `is_spawnable` / `is_summonable`

当前都为 `true`。

为什么要同时开：

- `is_spawnable` 允许它接入自然生成和刷怪蛋等流程。
- `is_summonable` 允许开发调试时用 `/summon` 直接验证。

#### 4.1.4 `properties`

这是当前项目最关键的部分之一。

原型普通螃蟹定义了 4 个属性：

- `fg:not_avoid`：布尔，是否标记为“当前不参与逃跑”
- `fg:in_avoid`：布尔，是否正处于逃跑状态
- `fg:attack_mode`：枚举，攻击动画模式
- `fg:attack_personality`：枚举，攻击人格

当前 7 个正式普通生态实体在此基础上还接入了驯服与背包状态：

- `fg:is_tamed`：布尔，当前是否已驯服
- `fg:has_backpack`：布尔，是否已装备蟹壳背包
- `fg:follow_state`：枚举，`follow` / `stay`，用于跟随 / 待命切换

护群螃蟹和暴躁螃蟹保留了后两个攻击属性。

为什么当前项目选择用 `properties`，而不是完全靠组件组名称推断状态：

- `property` 可以被动画控制器查询。
- `property` 可以按需 `client_sync`，让客户端动画状态机直接读到。
- `property` 适合表达“轻量状态值”，组件组适合表达“能力包”。

#### 4.1.5 `client_sync`

当前项目里：

- `fg:attack_mode` 是 `client_sync: true`
- `fg:attack_personality` 是 `client_sync: false`

为什么这样分：

- `attack_mode` 会被资源包动画控制器查询，用来决定播放左击、右击还是双击动作，所以客户端必须知道。
- `attack_personality` 只在服务端初始化攻击循环时使用，客户端不需要拿它直接做表现，所以没必要同步。

这是一条非常重要的规则：

> 只有“客户端表现真的要直接读取”的属性才开 `client_sync`。

#### 4.1.6 `animations` 和 `scripts.animate`

当前行为包里也有动画别名和 `scripts.animate`，例如普通螃蟹：

- `hurt_event`
- `reset_not_avoid`
- `reset_attack_model`
- `attack_switch`

为什么行为包里也需要“动画”和“动画控制器”：

- 这里不是做模型动作，而是在借用 Bedrock 的动画状态机系统做逻辑驱动器。
- 比如 `attack_switch` 会在攻击中根据 `query.is_delayed_attacking` 进入不同状态。
- 比如 `hurt_event` 会借 `animation_length` 充当 2 秒计时器。

## 5. `component_groups`：承载“可切换状态”

当前项目里的组件组有三类。

### 5.1 愤怒类组件组

普通螃蟹有：

```json
"groups:untamed_anger": {
  "minecraft:angry": {
    "duration": 25,
    "broadcast_anger": false,
    "broadcast_anger_on_being_attacked": false
  }
}
```

护群螃蟹和暴躁螃蟹则把广播打开，并设置：

- `broadcast_range`
- `broadcast_targets`

为什么要单独拆出愤怒组件组：

- 因为“是否愤怒”是状态，不是实体恒定底层属性。
- 以后如果要加入“受伤后才激活”“某阶段增强愤怒”“脱战后移除愤怒”等逻辑，组件组天然适合做动态加减。

### 5.2 避让组件组

只有普通螃蟹有：

```json
"groups:avoid_another_mob": {
  "minecraft:behavior.avoid_mob_type": { ... }
}
```

当前配置要点：

- `priority: 0`
- `max_dist: 16`
- `max_flee: 16`
- `walk_speed_multiplier: 2.0`
- `sprint_speed_multiplier: 3.0`
- 过滤条件是 `other` 不是 `fg_crab_normal`

为什么避让行为一定要做成独立组件组，而不是默认就挂在 `components` 里：

- 因为普通螃蟹不是常驻逃跑型，它只在特定事件后才进入避让。
- 如果默认常驻，它会一直逃，攻击和逛街逻辑都会被打断。

### 5.3 攻击组件组

三个实体都拆成：

- `groups:attack_left`
- `groups:attack_right`
- `groups:attack_double`

每组里都包含：

- `minecraft:attack`
- `minecraft:behavior.delayed_attack`

为什么要拆成 3 个组，而不是一个攻击组件里做全部变化：

- 当前的“左击 / 右击 / 双击”不只是动画不同，数值节奏也不同。
- 每次切换前先 remove 再 add，可以保证互斥能力组不会并存。

### 5.4 驯服跟随组件组

7 个正式普通生态实体在驯服后会挂上：

- `groups:tamed_behavior`：承载 `minecraft:is_tamed`、主人受伤目标响应等通用驯服能力。
- `groups:tamed_follow`：承载 `minecraft:behavior.follow_owner`。
- `groups:tamed_stay`：临时把移动速度降为 0，用于 MVP 的待命状态。

为什么把跟随拆出 `groups:tamed_follow`：

- 跟随和待命是互斥状态。
- 只把 `follow_owner` 从通用驯服组里拆出去，才能在不移除 `minecraft:is_tamed` 的情况下切换待命。
- 后续如果改成更完整的坐下 / 待命动画，只需要替换 `groups:tamed_stay` 的能力表达。

## 6. `components`：默认常驻能力

当前三个实体的 `components` 主体非常一致，这说明项目已经形成了一套基础螃蟹模板。

### 6.1 `minecraft:type_family`

普通螃蟹当前 family：

- `mob`
- `animal`
- `crab`
- `fg_crab`
- `fg_crab_normal`

为什么 family 要同时保留“通用层”和“具体层”：

- `mob` / `animal` 用于接入更通用的生态判断。
- `crab` / `fg_crab` 用于模块内统一识别。
- `fg_crab_normal` 用于区分具体子类。

### 6.2 导航与物理

当前用了：

- `minecraft:navigation.walk`
- `minecraft:jump.static`
- `minecraft:physics`
- `minecraft:pushable`

导航配置中关键的是：

- `can_path_over_water: false`
- `can_sink: false`
- `can_float: true`
- `avoid_water: false`

为什么这样组合：

- 螃蟹生态在海边，所以不能把水完全视为禁区。
- 但它又不是专门的游泳单位，所以不让它“跨水寻路”。
- `can_float: true` 可以减少海岸线附近被水体拖死的情况。

### 6.3 基础 AI

当前基础行为包括：

- `minecraft:behavior.float`
- `minecraft:behavior.random_stroll`
- `minecraft:behavior.look_at_player`
- `minecraft:behavior.random_look_around`
- `minecraft:behavior.hurt_by_target`

特别注意 `hurt_by_target`：

```json
"minecraft:behavior.hurt_by_target": {
  "priority": 1,
  "alert_same_type": false
}
```

为什么 `alert_same_type` 当前刻意设为 `false`：

- 因为项目把“群体响应”交给更可控的 `minecraft:angry.broadcast_*` 和自定义事件链。
- 如果这里直接自动警报同类，会和自定义受伤逻辑叠加，造成行为失控。

## 7. `events`：把状态切换串成闭环

### 7.1 出生初始化事件 `minecraft:entity_spawned`

普通螃蟹出生时会：

1. 添加 `groups:untamed_on_hurt_avoid`
2. 移除全部攻击组
3. 触发 `fg:reset_attack_cycle_by_personality`

护群螃蟹和暴躁螃蟹则会：

1. 添加 `groups:untamed_anger`
2. 移除全部攻击组
3. 触发 `fg:reset_attack_cycle_by_personality`

为什么出生时一定先“清空攻击组，再按人格重建”：

- 防止以后复制实体文件时残留默认攻击组。
- 把“初始化默认攻击形态”统一收口到一个事件里，后续如果人格规则变化，只改一处。

### 7.2 攻击人格重置事件 `fg:reset_attack_cycle_by_personality`

当前逻辑：

- 如果人格是 `calm`，挂 `groups:attack_left`，并把 `fg:attack_mode` 设成 `attack_left`
- 如果人格是 `aggressive`，挂 `groups:attack_double`，并把 `fg:attack_mode` 设成 `attack`

为什么要同时“加组件组 + 设属性”：

- 加组件组解决服务端实际攻击能力。
- 设属性解决客户端动画显示和后续状态机判断。

### 7.3 攻击切换事件 `fg:switch_to_attack_left/right/double`

这三组事件都遵守同一模板：

1. 移除全部攻击组
2. 添加目标攻击组
3. 更新 `fg:attack_mode`

为什么一定做成三个明确事件，而不是一个事件里用复杂分支判断：

- 当前攻击切换是固定环：左 -> 右 -> 双 -> 左。
- 分成离散事件后，动画时间轴只需要触发下一个事件名，结构更清楚。

### 7.4 普通螃蟹受伤逻辑 `fg:on_hurt_event`

事件做了三件事：

1. 给自己加 `groups:untamed_anger`
2. 把自己 `fg:not_avoid` 设为 `true`
3. 用命令让半径 16 内其他普通螃蟹触发 `fg:avoid_another_mob`

为什么要先把自己标成 `not_avoid=true`：

- 因为后面的选择器只选 `has_property={fg:not_avoid=false}` 的普通螃蟹。
- 这样受伤的那一只不会把自己也算进“需要逃跑的同类”里。

### 7.5 普通螃蟹恢复事件

普通螃蟹还有两个恢复事件：

- `fg:recover_not_avoid_event`
- `fg:recover_avoid_event`

为什么恢复要拆两个事件：

- `not_avoid` 和 `in_avoid` 语义不同。
- 一个是“我是例外，不参与逃跑”。
- 一个是“我正处于逃跑状态”。

## 8. 行为包动画与动画控制器为什么存在

当前行为包里有两个关键文件：

- `fg_more_crabBehaviorPack/animations/fg_crab.animation.json`
- `fg_more_crabBehaviorPack/animation_controllers/fg_crab.ac.json`

### 8.1 行为包 `animations/fg_crab.animation.json`

当前实际起作用的逻辑动画有 4 个：

- `animation.fg_crab.switch_attack_left`
- `animation.fg_crab.switch_attack_right`
- `animation.fg_crab.switch_attack_double`
- `animation.fg_crab.in_avoid_timeline`

前三个动画的核心不是动作，而是 `timeline` 事件。

为什么用动画时间轴触发事件：

- `minecraft:behavior.delayed_attack` 本身是带攻击持续时间的。
- 让时间轴在攻击后半段切到下一个攻击模式，可以稳定形成“攻击节奏链”。

`animation.fg_crab.in_avoid_timeline` 只有长度，没有关键帧。

为什么一个“空动画”反而有价值：

- 它充当了一个 2 秒计时器。
- 控制器只要监听 `query.any_animation_finished`，就知道“逃跑时段结束了”。

### 8.2 行为包 `animation_controllers/fg_crab.ac.json`

当前有 4 个行为控制器：

- `controller.animation.fg_crab.attack_switch`
- `controller.animation.fg_crab.reset_attack_model`
- `controller.animation.fg_crab.reset_not_avoid`
- `controller.animation.fg_crab.hurt_event`

其中最关键的是：

- `attack_switch` 负责在 delayed attack 期间驱动攻击模式循环
- `reset_attack_model` 负责脱战后重置起手式
- `reset_not_avoid` 和 `hurt_event` 负责普通螃蟹的受伤状态生命周期

## 9. 当前攻击循环是怎么工作的

原型三只螃蟹都共享一套攻击循环；当前 7 个普通生态变体也沿用了这套基础攻击与表现结构。

```text
entity_spawned
  -> reset_attack_cycle_by_personality
  -> 挂上某个 attack_* 组件组
  -> delayed_attack 生效
  -> 行为控制器 attack_switch 检测到 query.is_delayed_attacking
  -> 播放对应逻辑动画
  -> 时间轴触发下一种 attack_* 事件
  -> 下一次攻击用新的参数
```

为什么要用“人格 + 循环”两层设计：

- 当前人格只决定起手式。
- 之后统一进入共用攻击循环。
- 这样能保证同一套动画、状态机和数值结构可以复用。

当前数值差异：

| 实体 | 左击伤害 | 右击伤害 | 双击伤害 |
|---|---:|---:|---:|
| `fg:crab` | 2 | 2 | 4 |
| `fg:crab_help` | 2 | 2 | 4 |
| `fg:crab_aggressive` | 3 | 3 | 6 |

## 10. 当前普通螃蟹的“受伤后周围同类逃跑”是怎么工作的

这是当前行为包里最复杂、也最值得复用的一条链。

```text
普通螃蟹受伤
  -> fg:on_hurt_event
  -> 自己进入 angry，并标记 not_avoid = true
  -> 周围普通螃蟹触发 fg:avoid_another_mob
  -> 周围普通螃蟹 in_avoid = true，并挂上 avoid 组件组
  -> hurt_event 控制器检测到 in_avoid
  -> 播放 2 秒空动画
  -> on_exit 广播 fg:recover_avoid_event
  -> 移除避让组，清掉 in_avoid
```

为什么这条链分这么多段：

- “谁留下战斗”是一个问题。
- “谁进入逃跑”是另一个问题。
- “逃跑多久”又是第三个问题。

如果把这三件事挤在一个事件里，后续几乎没法单独调时长、目标和恢复条件。

## 11. `spawn_rules/*.json`

原型三个生成规则文件结构一致，关键字段包括：

- `population_control: "animal"`
- `minecraft:spawns_on_surface`
- `minecraft:spawns_on_block_filter`
- `minecraft:brightness_filter`
- `minecraft:height_filter`
- `minecraft:weight`
- `minecraft:herd`
- `minecraft:density_limit`
- `minecraft:biome_filter`

为什么生成规则必须独立维护：

- 生成地点是生态设计，不是实体 AI 本体。
- 后续要平衡稀有度时，改 `weight` 和 `herd` 就够，不需要碰实体文件。

当前权重：

- 普通螃蟹：6
- 护群螃蟹：4
- 暴躁螃蟹：2

为什么权重差异化很重要：

- “更强的怪更少见”优先应该用生成概率控制，而不是只靠堆高数值。

## 12. `loot_tables/entities/*.json`

当前掉落表都是两池结构：

1. 掉 `fg:crab_claws`
2. 掉 `fg:crab_shell_powder`

为什么拆成两个 pool，而不是都塞在一个 entries 里：

- 两种资源的平衡节奏不同。
- 以后如果想给壳粉追加额外条件、稀有掉落或幸运影响，单独一池更容易扩展。

当前数值：

| 掉落表 | 蟹钳数量 | 壳粉数量 |
|---|---:|---:|
| `fg_crab.json` | 1 到 2 | 0 到 1 |
| `fg_crab_help.json` | 1 到 2 | 0 到 1 |
| `fg_crab_aggressive.json` | 1 到 3 | 0 到 2 |

需要特别注意一个现状：

- `fg_more_crabBehaviorPack/loot_tables/entities/fg_crab_aggressive.json` 已经存在更高掉落版本。
- 但 `fg_more_crabBehaviorPack/entities/fg_crab_aggressive.json` 当前实际引用的是 `loot_tables/entities/fg_crab_help.json`。

这说明文档里必须区分“仓库已准备的资源”和“当前实际运行的引用”。

## 13. 基于当前架构新增一只生物，推荐顺序

1. 复制最接近的 `entities/*.json`
2. 第一时间统一 `identifier`
3. 先想清楚哪些是 `properties`，哪些是 `component_groups`
4. 先做出生初始化事件，再做运行中切换
5. 最后接 `spawn_rules` 和 `loot_tables`

为什么推荐这个顺序：

- 当前项目最容易漏的是跨文件关联和状态生命周期。
- 先把主键和状态骨架定稳，再接自然生成与掉落，排查成本最低。

当前扩展经验：

- 普通生态变体适合继续复用原型螃蟹的 JSON 模板。
- 矿物螃蟹虽然拆成 9 个实体，但吃矿行为应收口到服务端脚本和共享事件，避免 9 份逻辑分叉。
- 海盗螃蟹的偷窃、返还和逃跑状态回落依赖脚本状态表，不建议只靠 JSON AI 硬拼。
- 捕蟹笼是实体版 MVP，行为核心在脚本侧维护等待、诱饵、收获和破坏概率。

## 14. 当前架构下最容易犯的错误

- 只改 `fg:attack_mode`，忘了切组件组
- 只加新攻击组，不先移除旧攻击组
- 给不会被客户端读取的属性也开 `client_sync`
- 把群体联动同时交给 `hurt_by_target` 和 `angry.broadcast_*`
- 修改掉落表文件，但忘了实体文件还在引用旧表
- 只做 biome 过滤，不做地表方块过滤

为什么这些错误高频：

- 当前项目是“状态 + 能力 + 事件 + 控制器”四层联动。
- 只改其中一层，通常不会立刻报语法错，但运行表现会偏。

## 15. 推荐检查清单

- `identifier` 是否全链路一致
- `type_family` 是否同时包含通用层和变体层
- `properties` 是否只同步真正需要给客户端读的字段
- 互斥组件组切换时是否先 `remove`
- 属性更新和组件组更新是否成对出现
- `spawn_rules.description.identifier` 是否匹配
- 生成条件是否同时覆盖 biome、地表、亮度、高度
- `minecraft:loot.table` 是否指向期望的掉落表
- `scripts.animate` 是否挂上所需行为控制器
- 时间轴触发的事件名是否真实存在

## 16. 一句话总结

当前仓库的生物行为配置已经形成了比较清晰的模式：

> 用 `entities` 定义实体底座，用 `properties` 表示轻量状态，用 `component_groups` 承载可切换能力，用 `events` 做状态切换，用行为包动画控制器做时序和生命周期管理，用 `spawn_rules` 和 `loot_tables` 把生态与产出解耦。
