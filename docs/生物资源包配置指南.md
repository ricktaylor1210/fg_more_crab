# 生物资源包配置指南

## 1. 文档定位
这份文档基于当前仓库里已经接到实体上的资源包配置来整理，不讨论还没和行为包真正接线的预留资源。

当前实际纳入梳理范围的资源包文件有：

- `fg_more_crabResourcePack/entity/fg_crab.entity.json`
- `fg_more_crabResourcePack/entity/fg_crab_help.entity.json`
- `fg_more_crabResourcePack/entity/fg_crab_aggressive.entity.json`
- `fg_more_crabResourcePack/models/entity/crab/fg_crab.geo.json`
- `fg_more_crabResourcePack/animations/fg_crab.animation.json`
- `fg_more_crabResourcePack/animation_controllers/fg_crab.ac.json`
- `fg_more_crabResourcePack/render_controllers/mc_default.render.json`
- `fg_more_crabResourcePack/particles/fg_crab_angry.particle.json`
- `fg_more_crabResourcePack/textures/entity/crab/*.png`
- `fg_more_crabResourcePack/textures/item_texture.json`
- `fg_more_crabResourcePack/texts/zh_CN.lang`
- `fg_more_crabResourcePack/materials/entity.material`

这份指南重点解释两件事：

1. 当前三只螃蟹在客户端表现链路上是怎么接起来的。
2. 为什么当前项目采用“共用模型、共用动画、变体只换贴图和少量入口”的做法。

## 2. 当前项目里的资源包链路总览

按当前仓库的实际结构，一只生物在资源包侧的显示链路是：

```text
entity/*.entity.json
  -> 声明客户端实体入口
  -> 指向 geometry / textures / animations / render_controller / spawn_egg
models/entity/**/*.geo.json
  -> 定义骨骼和模型
animations/*.animation.json
  -> 定义具体动作、粒子事件、骨骼位移
animation_controllers/*.ac.json
  -> 根据 query 和 property 选择动画状态
render_controllers/*.render.json
  -> 把 Geometry.default / Texture.default / Material.default 实际取值接出来
textures/entity/**/*.png
  -> 提供实体贴图
textures/item_texture.json
  -> 提供刷怪蛋等物品图标索引
texts/*.lang
  -> 提供显示名称
particles/*.particle.json
  -> 提供附加表现
```

为什么必须按这条链理解，而不是只盯着 `client_entity`：

- `client_entity` 只是入口，不是全部。
- 入口只负责“引用关系”，真正的骨骼、动作、贴图和粒子都在其他文件里。

## 3. 当前三只螃蟹的资源配置策略

当前三个客户端实体的共同点非常明显：

- 共用同一个 geometry：`geometry.crab`
- 共用同一个主动画控制器：`controller.animation.fg_crab.base`
- 共用同一个姿态控制器：`controller.animation.fg_crab.sideways_pose`
- 共用同一套动作动画：`idle`、`walk`、`walk_attack`、`attack_left`、`attack_right`、`attack`
- 共用同一个渲染控制器：`controller.render.mc_default`
- 共用同一个粒子效果入口：`fg:crab_angry`

三者主要差异只有：

- `identifier`
- `textures.default`
- `spawn_egg.texture`

为什么这是当前项目里正确的做法：

- 这三只螃蟹骨架相同，动作逻辑也相同，差异主要是定位和强度。
- 这种情况下复用模型和动画，维护成本远低于复制三套资源。

## 4. `entity/*.entity.json`

当前三个入口文件结构完全一致，只改了个别字段。

### 4.1 `identifier`

当前分别是：

- `fg:fg_crab`
- `fg:fg_crab_help`
- `fg:fg_crab_aggressive`

为什么这里必须和行为包完全一致：

- 客户端实体是按 identifier 绑定到行为实体上的。
- 一旦不一致，最常见的结果不是报错，而是实体表现直接断链。

### 4.2 `materials`

当前都写成：

```json
"materials": {
  "default": "entity_alphatest"
}
```

为什么当前项目使用 `entity_alphatest`：

- 螃蟹贴图属于常见的带透明裁切的实体贴图。
- 当前仓库没有做自定义发光、半透明壳体、特殊描边等需求，没必要引入更复杂材质。

### 4.3 `textures`

当前三只螃蟹分别绑定：

- 普通螃蟹：`textures/entity/crab/fg_crab_orange`
- 护群螃蟹：`textures/entity/crab/fg_crab_red`
- 暴躁螃蟹：`textures/entity/crab/fg_crab_purple`

为什么当前差异只体现在 `textures.default`：

- 当前三只螃蟹骨骼结构完全一致，不需要换 geometry。
- 动作语义也一致，不需要换动画树。

### 4.4 `geometry`

当前都写成：

```json
"geometry": {
  "default": "geometry.crab"
}
```

为什么共用一个 geometry 是合理的：

- 当前三只螃蟹体型相同。
- 攻击动作、待机动作、移动动作都依赖相同骨骼命名。

### 4.5 `animations`

当前 `client_entity` 里同时声明了：

- 控制器别名：`base_controller`、`sideways_pose_controller`
- 粒子触发动画：`angry_par`
- 基础动作：`idle`、`walk`、`walk_attack`
- 攻击动作：`attack_left`、`attack_right`、`attack`
- 姿态动作：`sideways_pose`

为什么这里要定义“别名层”：

- `client_entity` 用的是本地别名，底层再映射到具体动画资源名。
- 这样动画控制器里只依赖别名，不直接写长路径，后续换底层动画文件更容易。

### 4.6 `scripts.animate`

当前配置：

```json
"animate": [
  {
    "angry_par": "query.has_target"
  },
  "base_controller",
  "sideways_pose_controller"
]
```

为什么第一项是条件对象，而后面两项是控制器名：

- `angry_par` 不是常驻动作，它只有在 `query.has_target` 时才需要激活。
- `base_controller` 和 `sideways_pose_controller` 是常驻状态机，负责基础动作和待机姿态切换。

### 4.7 `particle_effects`

当前：

```json
"particle_effects": {
  "angry_par": "fg:crab_angry"
}
```

为什么这里需要一个别名映射：

- 动画里触发的是 `effect: "angry_par"`
- 真正粒子资源的 identifier 是 `fg:crab_angry`

### 4.8 `render_controllers`

当前都只挂：

```json
"render_controllers": [
  "controller.render.mc_default"
]
```

为什么当前项目只用一个通用渲染控制器：

- 这三只螃蟹没有多材质切换、骨骼层级换贴图、部件显隐渲染分流等复杂需求。
- 一个通用控制器就足够。

### 4.9 `spawn_egg`

当前分别绑定：

- `fg:fg_crab`
- `fg:fg_crab_help`
- `fg:fg_crab_aggressive`

为什么刷怪蛋贴图要在 `client_entity` 里声明，而不是只配 `item_texture.json`：

- `item_texture.json` 只是图集索引表。
- `spawn_egg.texture` 才是把“这个实体的蛋”指向那个索引键的地方。

## 5. `models/entity/crab/fg_crab.geo.json`

当前三只螃蟹共用 `geometry.crab`。

### 5.1 geometry 描述头

当前定义了：

- `identifier: "geometry.crab"`
- `texture_width: 64`
- `texture_height: 64`
- 可见范围宽高和偏移

为什么可见范围要显式设置：

- 这会影响客户端剔除和显示稳定性。
- 小型低矮生物如果 visible bounds 不合理，常见问题是视角稍远就被错误裁掉。

### 5.2 `root` 骨骼和 locator

`root` 是所有骨骼的上层节点，并且带了 `angry_locator`。

为什么 `root` 必须存在：

- 当前资源包的 `animation.fg_crab.sideways_pose` 会直接旋转 `root`。
- 如果没有统一根节点，整体朝向调整会被迫分散到多个骨骼上。

为什么模型里预留 `angry_locator` 是好事：

- 说明作者已经为粒子挂点精确定位预留了结构。
- 这能让后续粒子、投射物挂点、特效锚点有稳定位置。

需要注意的现状是：

- 当前 `animation.crab.angry_par` 触发粒子时只写了 `effect`，没有显式指定 `locator`。
- 所以 `angry_locator` 现在更像“已预留挂点”，而不是当前情绪粒子必然依赖的路径。

### 5.3 预留骨骼

当前 `geometry.crab` 里除了普通螃蟹结构，还包含：

- `crab_backpack`
- `ore`
- `ore1` 到 `ore8`
- `rightpliers_ore`
- `bone6`
- `bone7`

为什么三只普通螃蟹没用到矿物骨骼却仍然保留这些结构：

- 当前项目明显在为矿物螃蟹、背包螃蟹等后续变体做共模准备。
- 这样做的好处是：未来新变体可以继续复用同一个 geometry 和大量现有动画。

## 6. `animations/fg_crab.animation.json`

这个文件很大，因为它明显承担了“螃蟹通用动作库”的角色。

当前三只螃蟹实际直接用到的动画有：

- `animation.crab.angry_par`
- `animation.crab.idle`
- `animation.crab.walk`
- `animation.crab.walk_attack`
- `animation.crab.attack_left`
- `animation.crab.attack_right`
- `animation.crab.attack`
- `animation.fg_crab.sideways_pose`

为什么这里要先区分“已接线”和“未接线”：

- 文件里还有大量 `ore`、`eat`、`defense`、`lying_on_sand`、`climb_out` 等动画。
- 它们在资源库里存在，不代表当前三只实体已经在入口或控制器里实际使用。

### 6.1 `animation.crab.idle`

当前待机动画会：

- 身体轻微上下起伏
- 嘴部、眼部、触须做小动作
- 隐藏 `ore` / `rightpliers_ore` 等预留部件

为什么待机动画里还要显式隐藏预留部件：

- 因为当前 geometry 是共模。
- 不显式隐藏，未来预留的矿物结构就会在普通螃蟹身上露出来。

### 6.2 `animation.crab.walk`

当前行走动画主要驱动身体摆动、钳子摆动和腿部横移。

为什么移动动画要强调横摆：

- 螃蟹的识别感很大程度来自横向步态。

### 6.3 `animation.crab.walk_attack`

作用是“保留移动节奏，同时把钳子抬高到攻击预备位”。

为什么单独做 `walk_attack`：

- 当前状态机允许“有目标但尚未正式进入 delayed attack”的阶段。
- 这个阶段如果继续播放普通 `walk`，会显得准备动作不足。

### 6.4 `animation.crab.attack_left/right/attack`

为什么必须拆成三套：

- 当前左右攻击和双击的骨骼位移并不完全对称。
- 服务端行为也已经拆成三种攻击模式。

### 6.5 `animation.fg_crab.sideways_pose`

当前只做一件事：

```json
"root": {
  "rotation": [0, 90, 0]
}
```

为什么这个简单动画很重要：

- 当前项目用一个常驻姿态动画，让它在非战斗时保持更符合螃蟹横移感的朝向。

### 6.6 `animation.crab.angry_par`

当前定义了粒子事件：

```json
"particle_effects": {
  "0.0": {
    "effect": "angry_par"
  }
}
```

为什么把情绪粒子做成单独动画：

- `scripts.animate` 只需要决定“是否激活 angry_par”，不用关心底层粒子具体何时发。

## 7. `animation_controllers/fg_crab.ac.json`

当前客户端有两个控制器。

### 7.1 `controller.animation.fg_crab.base`

这个控制器负责在以下状态间切换：

- `idle`
- `walk`
- `walk_attack`
- `attack_left`
- `attack_right`
- `attack`

它依赖的关键查询有：

- `query.ground_speed`
- `query.has_target`
- `query.is_delayed_attacking`
- `query.property('fg:attack_mode')`

为什么这套状态机设计是合理的：

- `ground_speed` 区分静止和移动
- `has_target` 区分游荡和战斗警戒
- `is_delayed_attacking` 区分准备中和正式挥击中
- `attack_mode` 决定具体打哪一套挥击动画

### 7.2 为什么控制器要直接读取 `fg:attack_mode`

因为当前服务端和客户端共用同一套“攻击模式枚举语义”。

这背后依赖行为包里的一个关键前提：

- `fg:attack_mode` 开了 `client_sync: true`

### 7.3 `controller.animation.fg_crab.sideways_pose`

逻辑是：

- 默认在 `sideways`
- 有目标时退出 sideways
- 没目标时回 sideways

为什么姿态控制器要单独拆一个：

- 主控制器负责基础动作切换。
- 姿态控制器负责整体朝向修正。

## 8. `render_controllers/mc_default.render.json`

当前核心控制器内容非常简单：

```json
"controller.render.mc_default": {
  "geometry": "Geometry.default",
  "materials": [
    {
      "*": "Material.default"
    }
  ],
  "textures": ["Texture.default"]
}
```

为什么这里故意写得这么“空”：

- 它不决定具体用哪张图、哪个模型，而是把决定权交回 `client_entity.description`。
- 这意味着一个渲染控制器就能服务多个变体。

## 9. 粒子配置：`particles/fg_crab_angry.particle.json`

当前情绪粒子标识是：

```json
"identifier": "fg:crab_angry"
```

关键点包括：

- `material: particles_blend`
- 贴图：`textures/particle/angry_particle`
- `emitter_local_space.position: true`
- `spawn_rate: 1`
- `max_particles: 3`
- 发射器活动时长：2 秒
- 单粒子寿命：2 秒

为什么这样配置适合“敌意提示粒子”：

- 发射量少，不会遮挡本体。
- 生命周期短，不会在脱战后残留太久。
- 本地空间跟随实体，可以稳定漂在头顶附近。

## 10. 贴图与刷怪蛋图集配置

### 10.1 实体贴图

当前实体贴图在：

- `textures/entity/crab/fg_crab_orange.png`
- `textures/entity/crab/fg_crab_red.png`
- `textures/entity/crab/fg_crab_purple.png`

为什么实体贴图路径和 `client_entity.textures.default` 保持一一对应非常重要：

- render controller 最终只认 `Texture.default`
- 一旦路径写错，不会帮你自动回退到别的变体贴图

### 10.2 `textures/item_texture.json`

当前为刷怪蛋图标注册了：

- `fg:fg_crab`
- `fg:fg_crab_help`
- `fg:fg_crab_aggressive`

为什么刷怪蛋还要走 item texture 图集：

- 因为刷怪蛋本质上是物品图标，不是实体贴图。
- `spawn_egg.texture` 给的是图集键，不是图片文件路径本身。

## 11. 语言文件

当前 `texts/zh_CN.lang` 里包含：

- `entity.fg:fg_crab.name`
- `entity.fg:fg_crab_help.name`
- `entity.fg:fg_crab_aggressive.name`

为什么语言条目必须算进“生物资源包配置”：

- 玩家最终看到的名字来自这里，不来自行为包。
- 实体就算模型、贴图、动画都正常，没有名称条目也会出现显示缺失。

## 12. 当前资源包里“已接线内容”和“预留内容”怎么区分

当前三只螃蟹已明确接线的资源有：

- `geometry.crab`
- 基础移动和攻击动画
- 主动画控制器
- 姿态控制器
- 通用渲染控制器
- angry 粒子
- 三张实体贴图
- 三张刷怪蛋图标
- 三条实体名称

仓库中存在、但当前三只螃蟹未直接接线的同体系资源有：

- 矿物相关动作和骨骼
- 背包相关骨骼
- 吃矿、趴沙、爬出等动作

为什么一定要区分这两类：

- 已接线内容决定“现在能跑什么”。
- 预留内容决定“以后可能怎么扩展”。

## 13. 基于当前架构新增一个生物变体，资源包建议顺序

1. 先判断是否真的需要新 geometry
2. 新建 `entity/*.entity.json`
3. 能复用现有动画，就不要新开动画文件
4. 只有当表现语义变化时才加新动画别名
5. 如果新增粒子或挂点，优先延续 locator 思路

为什么推荐这个顺序：

- 当前项目最大的资源优势就是共模。
- 只要骨骼不分叉，后续动画、控制器和渲染配置都能继续复用。

## 14. 当前架构下最容易犯的资源配置错误

- 资源包 identifier 和行为包 identifier 不一致
- 改了 `spawn_egg.texture`，忘了 `item_texture.json`
- 新建 geometry 后，骨骼命名没和现有动画对齐
- 只改实体贴图，不检查动画里是否显隐了预留部件
- 在资源包控制器里读取了行为包未同步的属性
- 把所有差异都做成新贴图，但不检查 render controller 是否需要分支

为什么这些错误高频：

- 当前项目是“入口文件 + 共模 geometry + 共用动作库 + 跨包属性联动”的结构。
- 只改其中一层，通常不会立刻报语法错，但运行表现会偏。

## 15. 推荐检查清单

- `client_entity.identifier` 是否和行为包一致
- `textures.default`、`geometry.default` 是否存在
- 控制器里读取的 query / property 是否真实存在
- 动画别名是否和控制器引用名一致
- 共模隐藏逻辑是否覆盖了未使用部件
- 实体贴图路径是否真实存在
- `spawn_egg.texture` 是否在 `item_texture.json` 注册
- `entity.<identifier>.name` 是否存在
- 粒子 identifier 是否和 `particle_effects` 映射一致
- 如果用了 locator，动画事件是否真的显式引用了 locator

## 16. 一句话总结

当前仓库的生物资源包配置已经形成了很清晰的方向：

> 用 `client_entity` 做入口，用通用 `geometry` 和通用动画库承载同骨架螃蟹，用客户端控制器消费行为包同步过来的状态，用最少的贴图差异区分变体，用粒子、姿态和局部动作强化物种辨识度。
